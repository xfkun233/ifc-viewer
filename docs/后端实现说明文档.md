# IFC Viewer 后端实现说明文档

## 1. 文档目标与范围

本文档基于当前仓库 `apps/api` 的真实代码实现编写，目标是帮助开发、测试、运维和交接人员快速理解后端系统：

- 技术选型与运行方式
- 模块职责和关键调用链
- 数据模型与数据库迁移
- IFC 文件上传、去重、解析、快照写入的完整流程
- 覆盖层（自定义属性/标注）读写机制
- 错误处理、状态流转与排障建议

说明：本文只描述当前代码实现，不包含未来规划功能。

## 2. 后端整体架构

后端位于 `apps/api`，采用单服务架构：

- HTTP 框架：Fastify
- 语言：TypeScript（ESM）
- 数据访问：Prisma + MySQL
- IFC 解析：`web-ifc`
- 参数校验：Zod
- 文件存储：本地磁盘目录（`UPLOAD_DIR`）

核心特征：

- API 进程内置一个轮询 Worker，用于异步消费待同步模型队列。
- IFC 上传后先去重，再进入同步队列。
- 同步流程支持分块持久化，包含进度回写与失败重试。
- 采用双层属性模型：原生属性（NATIVE）与用户覆盖属性（CUSTOM）。

## 5. 数据库设计（Prisma）

Schema 文件：`apps/api/prisma/schema.prisma`

### 5.1 枚举

- `ModelSyncStatus`：`PENDING | PROCESSING | READY | FAILED`
- `PropertySource`：`NATIVE | CUSTOM`
- `PropertyValueType`：`STRING | LABEL | REAL | INTEGER | BOOLEAN`

### 5.2 表结构

1. `IfcModel`
- 模型主表，记录文件信息、去重指纹、同步状态和统计。
- 关键字段：
  - `fileHash`：完整文件哈希（用于同文件去重）
  - `sourceFingerprint`：基础 IFC 内容指纹（用于谱系）
  - `syncStatus/syncQueuedAt/syncProcessedElements`
  - `totalElements/totalProperties`
- 索引：`createdAt`、`fileHash`、`sourceFingerprint`、`(syncStatus,syncQueuedAt)`。

2. `IfcElement`
- 存储模型构件快照（按 `modelId + expressId` 唯一）。
- `attributesJson`：基础属性
- `rawDataJson`：提取器归一化后的原始结构（可为空）

3. `IfcElementProperty`
- 存储构件属性（原生+自定义）。
- 复合唯一键：`modelId + expressId + source + psetName + propertyName`。
- `numericValue/booleanValue/rawValueJson` 支撑类型化查询与回显。

4. `IfcAnnotation`
- 存储三维标注。
- 唯一键：`modelId + clientId`。

### 5.3 迁移演进

- `20260420000100_init`
  - 初始化 4 张表 + 外键 + 基础索引。

- `20260420000200_sync_queue_progress`
  - 给 `IfcModel` 增加：
  - `syncQueuedAt`
  - `syncProcessedElements`
  - 新索引 `IfcModel_syncStatus_syncQueuedAt_idx`

该迁移体现了队列可观测性增强（排队时间与处理进度可落库）。

## 6. HTTP API 详细说明

所有接口前缀来自 `app.register(..., { prefix: '/api' })`。

### 6.1 健康检查

- `GET /api/health`
  - 返回：`{ status: 'ok', timestamp }`

### 6.2 模型与队列

- `GET /api/models`
  - 最近模型列表（默认最多 10 条，按创建时间倒序）。

- `GET /api/sync-queue`
  - 队列可视化列表（最多 100 条）。
  - service 层按状态优先级排序：`PROCESSING > PENDING > FAILED > READY`。

- `POST /api/models/upload`
  - multipart 上传 IFC。
  - 成功返回 201 + 模型对象。

- `GET /api/models/:modelId`
  - 查询模型详情。

- `POST /api/models/:modelId/requeue-sync`
  - 强制重入队（状态重置为 PENDING）。

- `GET /api/models/:modelId/file`
  - 下载原始 IFC 文件流。
  - 会更新 `lastAccessedAt`。

### 6.3 快照生命周期（供前端或 worker 写入）

- `POST /api/models/:modelId/snapshot/start`
  - 参数：`totalElements`, `totalChunks`
  - 将模型置为 `PROCESSING` 并清空旧 NATIVE 数据。

- `POST /api/models/:modelId/snapshot/chunk`
  - 参数：`chunkIndex`, `elements[]`
  - 分块写入构件 + 原生属性。

- `POST /api/models/:modelId/snapshot/complete`
  - 参数：`totalElements`, `totalProperties`
  - 标记 `READY` 并写入总量。

- `POST /api/models/:modelId/snapshot/fail`
  - 参数：`reason`
  - 标记 `FAILED` 并保存失败原因。

### 6.4 覆盖层（自定义属性/标注）

- `GET /api/models/:modelId/overlays`
  - 返回：`customProperties[]`, `annotations[]`

- `POST /api/models/:modelId/overlays/bootstrap`
  - 批量初始化覆盖层（幂等 upsert）。

- `PUT /api/models/:modelId/custom-properties`
  - 新增/更新单条 CUSTOM 属性。

- `DELETE /api/models/:modelId/custom-properties/:propertyId`
  - 删除单条 CUSTOM 属性。

- `PUT /api/models/:modelId/annotations`
  - 新增/更新单条标注（按 `clientId` 幂等）。

- `DELETE /api/models/:modelId/annotations/:annotationId`
  - 删除单条标注（`annotationId` 实际传 `clientId`）。

## 7. 关键业务流程

### 7.1 IFC 上传与去重

入口：`ModelService.uploadModel()`。

流程：

1. 校验扩展名必须为 `.ifc`。
2. 计算谱系信息（`deriveIfcLineage`）：
   - `fileHash`：完整文件哈希
   - `baseContentHash`：去自定义区后的 IFC 内容哈希
   - `sourceFingerprint`：优先使用嵌入元数据，否则回退 `baseContentHash`
3. 若 IFC 内嵌元数据存在且 `sourceFingerprint` 与 `baseContentHash` 不一致，拒绝上传（`IFC_HASH_VALIDATION_FAILED`）。
4. 按 `fileHash` 查询可复用模型：
   - 优先复用 `READY`
   - 其次 `PROCESSING`
   - 其次 `PENDING`
   - 最后任意最近记录
5. 若命中且状态为 `FAILED`，重排队并触发 worker。
6. 若未命中，保存文件到磁盘，创建模型记录，置为 `PENDING`，通知 worker。

### 7.2 后台队列消费

入口：`ModelSyncWorker.start()`。

机制：

- 启动时先调用 `requeueInterruptedSnapshots()`：把上次进程异常退出导致的 `PROCESSING` 模型重置为 `PENDING`。
- `setInterval` 每 2 秒触发 `tick()`。
- `processing` 标记防止并发重入。
- `claimNextQueuedModel()` 原子化抢占：仅从 `PENDING` 更新到 `PROCESSING` 成功者继续处理。

### 7.3 IFC 提取与落库

`processModel()` 核心步骤：

1. 读取本地 IFC 文件。
2. 调用 `backendIfcSnapshotExtractor.extractFromBuffer()`：
   - 扫描 IFC element 类型并收集 `expressId`
   - 排序后按 20 条一个 chunk 提取
3. 每个 chunk 回调内：
   - 首块触发 `startSnapshot()`（清旧数据、写初始状态）
   - `saveSnapshotChunk()` 落库
   - 更新 `syncProcessedElements`
4. 所有 chunk 成功后 `completeSnapshot()` -> `READY`。
5. 任何错误都 `failSnapshot()` -> `FAILED`，并记录 error message。

### 7.4 覆盖层读写

- CUSTOM 属性和标注不与 NATIVE 属性混用。
- bootstrap / upsert 都使用复合唯一键进行幂等写入。
- 删除操作会先校验存在性，不存在返回 404。

## 8. 提取器与数据归一化细节

文件：`model-sync.extractor.ts`

提取策略：

- 通过 `web-ifc` 获取：
  - `getItemProperties`
  - `getPropertySets`
  - `getTypeProperties`
  - `getMaterialsProperties`
- 跳过逆向关系键（如 `IsDefinedBy` 等）避免噪声。
- 属性值优先取 `NominalValue`，并兼容 `Length/Area/Volume/...` 等候选字段。
- 根据 value 与 type hint 归一化为 `PropertyValueType`。
- 用 `Map` 以 `pset::propertyName` 去重。

`rawData` 处理：

- 深度限制 12 层，防止超深结构。
- 检测循环引用，标记为 `[Circular]`。
- 最终输出 JSON 友好结构。

## 9. 大批量写入与 MySQL 包体保护

实现文件：`model.repository.ts`

### 9.1 双阈值分批策略

- 元素批次上限：`ELEMENT_MAX_BATCH_ROWS = 50`
- 属性批次上限：`PROPERTY_MAX_BATCH_ROWS = 200`
- 单批估算大小上限：`MAX_BATCH_BYTES = 1MB`

分批执行条件：

- 达到最大行数，或
- 继续追加将超过最大字节阈值

### 9.2 超大行保护

- 若单条记录估算字节超过 `MAX_BATCH_BYTES`，抛出：
  - code: `SNAPSHOT_ROW_TOO_LARGE`
  - status: `413`

### 9.3 原始数据降级保护

- `rawDataJson` 单元素上限：`MAX_RAW_DATA_BYTES_PER_ELEMENT = 512KB`
- 超限时不报错，而是写 `DbNull` 并输出 warning 日志。

### 9.4 事务超时调整

`saveSnapshotChunk()` 的 Prisma transaction 配置：

- `maxWait: 10000`
- `timeout: 60000`

用于降低大模型写入时事务超时风险。

## 10. 错误处理与返回约定

统一处理：`set-error-handler.ts`

- `AppError`
  - 使用业务状态码和业务错误码（`{ code, message }`）。

- `ZodError`
  - 返回 `400 VALIDATION_ERROR`，附 `issues`。

- 其他异常
  - 返回 `500 INTERNAL_SERVER_ERROR`。

常见业务错误码：

- `FILE_REQUIRED`：未上传文件
- `INVALID_FILE_TYPE`：非 IFC 文件
- `IFC_HASH_VALIDATION_FAILED`：谱系校验失败
- `MODEL_NOT_FOUND`：模型不存在
- `CUSTOM_PROPERTY_NOT_FOUND`：自定义属性不存在
- `ANNOTATION_NOT_FOUND`：标注不存在
- `SNAPSHOT_ROW_TOO_LARGE`：单条快照数据超限

## 11. 状态机与一致性策略

`IfcModel.syncStatus` 状态流转：

- 上传入队：`PENDING`
- worker 抢占：`PROCESSING`
- 成功完成：`READY`
- 任意异常：`FAILED`

重启恢复：

- 服务启动时自动把遗留 `PROCESSING` 重置回 `PENDING` 并写入错误原因。

重试机制：

- 可通过 `requeue-sync` 手工重排队。
- 上传命中 `FAILED` 的可复用记录时也会自动重排队。

## 12. 文件存储策略

- 上传文件保存至 `UPLOAD_DIR`（默认 `apps/api/storage/uploads` 的绝对路径）。
- 存储文件名使用 UUID，避免冲突与路径注入风险。
- 数据库保存：
  - `originalFileName`（回显/下载展示）
  - `storedFileName`（内部定位）
- 下载接口通过流读取物理文件返回。

## 5. 核心业务链路

## 5.1 IFC 上传与去重链路

入口：`POST /api/models/upload`

处理步骤：

1. 读取 multipart 文件。
2. 文件类型校验：必须是 `.ifc` 后缀，否则抛 `INVALID_FILE_TYPE`。
3. 调用 `deriveIfcLineage(buffer)` 计算：
   - `fileHash`：整文件 SHA-256
   - `baseContentHash`：去掉自定义区后的基础 IFC 内容哈希
   - `sourceFingerprint`：优先取嵌入元数据中的源指纹，否则退化为 `baseContentHash`
4. 若文件内含历史元数据且 `embeddedMetadata.sourceFingerprint !== baseContentHash`，拒绝上传（哈希校验失败）。
5. 用 `fileHash` 查重（`findModelsByFileHash`）：
   - 优先复用状态：`READY > PROCESSING > PENDING > 其他`
   - 若命中 `FAILED`，自动 requeue 并唤醒 Worker
   - 其余状态直接返回已存在模型
6. 未命中复用时：
   - 写本地文件（UUID 文件名）
   - 新建 `IfcModel`
   - 置为 `PENDING` 并设置 `syncQueuedAt`
   - `modelSyncWorker.notify()` 触发尽快处理

说明：当前哈希校验失败提示文案存在乱码现象（字符串编码问题），不影响逻辑分支本身。

## 5.2 同步队列与状态机

模型同步状态（`ModelSyncStatus`）：

- `PENDING`：等待处理
- `PROCESSING`：处理中
- `READY`：完成可用
- `FAILED`：失败

状态流转主路径：

- 上传新模型：`PENDING`
- Worker 抢占成功：`PROCESSING`
- 处理成功：`READY`
- 处理异常：`FAILED`
- 手动重试：`FAILED/READY/... -> PENDING`

Worker 机制（`model-sync.worker.ts`）：

- 定时轮询：每 2 秒 `tick()` 一次
- 并发保护：`processing` 标志保证单实例串行消费
- 抢占策略：`claimNextQueuedModel()` 按 `syncQueuedAt asc, createdAt asc` 取最老待处理项
- 乐观抢占：`updateMany(where: id + syncStatus=PENDING)`，防止并发实例重复消费
- 空闲唤醒：上传或重排队后 `notify()` 立即触发一次 `tick`

## 5.3 快照抽取与落库

Worker 处理单模型时（`processModel`）：

1. 读取 IFC 本地文件。
2. 调用 `backendIfcSnapshotExtractor.extractFromBuffer` 分块抽取。
3. 首个 chunk 到达时执行 `startSnapshot(modelId, totalElements)`：
   - 删除历史原生快照（`IfcElement` + `NATIVE` 属性）
   - 重置进度和状态
4. 每个 chunk：
   - `saveSnapshotChunk(modelId, elements)` 写入元素与原生属性
   - `updateSnapshotProgress(modelId, processedElements)` 更新进度
5. 全部完成后 `completeSnapshot(modelId, totals)`。
6. 异常则 `failSnapshot(modelId, reason)`。

提取器逻辑（`model-sync.extractor.ts`）：

- 遍历 IFC entity type，仅处理 `IsIfcElement(entityType)` 为真的元素。
- 每个元素并行读取：
  - `getItemProperties`
  - `getPropertySets`
  - `getTypeProperties`
  - `getMaterialsProperties`
- 对属性做规范化：
  - 从 `NominalValue / LengthValue / ...` 取值
  - 推断 `valueType`（`BOOLEAN/INTEGER/REAL/LABEL/STRING`）
  - `(psetName, propertyName)` 去重
- 构建两类数据：
  - 轻量字段（globalId/entityType/name/... + attributes）
  - `rawData`（深度限制 + 循环引用防护）
- 固定 chunk 大小：20 个元素。

## 6. 数据库设计

## 6.1 模型概览（schema.prisma）

1. `IfcModel`
   - 文件级元数据、同步状态、统计信息、时间戳。

2. `IfcElement`
   - 构件主表，唯一键 `(modelId, expressId)`。
   - 存基础字段与 `attributesJson`、`rawDataJson`。

3. `IfcElementProperty`
   - 构件属性表，含来源 `NATIVE/CUSTOM`。
   - 唯一键 `(modelId, expressId, source, psetName, propertyName)`。
   - 同时保留 `valueText`、`numericValue`、`booleanValue`、`rawValueJson`，便于展示与查询兼顾。

4. `IfcAnnotation`
   - 三维标注，唯一键 `(modelId, clientId)`。

## 6.2 索引策略

- `IfcModel`：`createdAt`、`fileHash`、`sourceFingerprint`、`(syncStatus, syncQueuedAt)`
- `IfcElement`：`(modelId, expressId)`
- `IfcElementProperty`：`(modelId, expressId, source)`、`(modelId, source)`
- `IfcAnnotation`：`modelId`

## 6.3 迁移演进

1. `20260420000100_init`
   - 初始化四张核心表及外键。

2. `20260420000200_sync_queue_progress`
   - 为 `IfcModel` 增加：
     - `syncQueuedAt`
     - `syncProcessedElements`
   - 增加索引 `IfcModel_syncStatus_syncQueuedAt_idx`。

该演进使“排队顺序”和“进度显示”具备可查询性。

## 7. API 详细说明

统一前缀：`/api`

## 7.1 健康检查

### GET /health

- 响应：
  - `status: ok`
  - `timestamp: ISO 时间`

## 7.2 模型与队列

### GET /models

- 说明：按创建时间倒序返回最近模型（默认 10）。

### GET /sync-queue

- 说明：返回队列视图（服务层按状态优先级排序：`PROCESSING > PENDING > FAILED > READY`）。

### POST /models/upload

- 入参：multipart 文件（单文件）
- 成功：`201 { item }`

  - `400 FILE_REQUIRED`
  - `400 INVALID_FILE_TYPE`
  - `400 IFC_HASH_VALIDATION_FAILED`

### GET /models/:modelId

- 说明：获取单模型。
- 失败：`404 MODEL_NOT_FOUND`

### POST /models/:modelId/requeue-sync

- 说明：手动重排队。
- 成功：`202 { item }`

### GET /models/:modelId/file

- 说明：下载 IFC 原始文件。
- 响应头：
  - `content-type`：模型 MIME
  - `content-disposition`：attachment 文件名

## 7.3 快照生命周期接口

这组接口可被前端主动调用，也可用于调试/补偿流程。

### POST /models/:modelId/snapshot/start

- 入参：
  - `totalElements: number >= 0`
  - `totalChunks: number > 0`
- 成功：`202`

### POST /models/:modelId/snapshot/chunk

- 入参：
  - `chunkIndex: number >= 0`
  - `elements: SnapshotElement[]`
- `SnapshotElement` 关键字段：
  - `expressId`
  - `globalId/entityType/name/objectType/predefinedType`
  - `attributes`
  - `rawData`
  - `properties[]`
- 成功：`202`，返回当前 chunk 写入计数。
- 失败：
  - `413 SNAPSHOT_ROW_TOO_LARGE`（单条记录超过批次字节阈值）

### POST /models/:modelId/snapshot/complete

- 入参：
  - `totalElements`
  - `totalProperties`
- 成功：`200`，状态切到 `READY`。

### POST /models/:modelId/snapshot/fail

- 入参：`reason`（可空）
- 成功：`200`，状态切到 `FAILED`。

## 7.4 覆盖层（自定义属性 + 标注）

### GET /models/:modelId/overlays

- 返回：
  - `customProperties[]`（source = CUSTOM）

### POST /models/:modelId/overlays/bootstrap

- 入参：
  - `customProperties[]`

### DELETE /models/:modelId/custom-properties/:propertyId

## 8. 校验与错误处理

## 8.1 输入校验

- 所有关键 body 和 params 使用 Zod 解析。
- 校验失败统一进入 `ZodError` 分支，返回：
  - `400`
  - `code: VALIDATION_ERROR`
  - `issues: [...]`

## 8.2 业务异常

- 统一抛 `AppError(message, statusCode, code)`。
- 全局处理器将其直接映射为对应 HTTP 状态与 `{ code, message }`。

## 8.3 未知异常

- 返回 `500 INTERNAL_SERVER_ERROR`。
- 同时记录：
  - `console.error`（含请求方法和 URL）
  - `request.log.error`

## 9. 性能与稳定性设计

## 9.1 批量写入防护

快照入库使用双阈值批量策略（见 `model.repository.ts`）：

- 元素批次上限：50 行
- 属性批次上限：200 行
- 单批估算字节上限：1MB

目标：避免 `createMany` 生成过大的 SQL 包触发 MySQL `max_allowed_packet` 错误。

另外，单条 `rawDataJson` 超过 512KB 时会被丢弃（写 `DbNull`），并打印告警日志。

## 9.2 事务与超时配置

`saveSnapshotChunk` 在事务中执行删除+写入，显式配置：

- `maxWait: 10000`
- `timeout: 60000`

用于缓解大模型写入时默认事务超时过短的问题。

## 9.3 并发与幂等

- 队列抢占使用乐观条件更新，减少重复消费。
- 覆盖层写入大量使用 `upsert`，天然幂等。
- 快照 chunk 写入前先按 `expressId` 删除旧数据，保障同一元素重复提交时结果可覆盖。

## 12. 已知风险与改进方向

1. 当前队列为进程内轮询 Worker，不具备多实例协调能力。
2. 上传哈希校验失败提示文本存在乱码，建议修正源码编码。
3. 文件存储为本地磁盘，横向扩展时建议迁移对象存储。
4. 快照抽取耗时与模型规模强相关，后续可考虑：
   - 独立任务队列（Redis/BullMQ）
   - 后台任务并发控制与可观测指标
   - 分层缓存（热模型）
